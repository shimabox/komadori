## 背景・目的

抽出結果は小さなサムネイル(320〜400px JPEG)の一覧でしか確認できず、細部の確認や「どのフレームを採用するか」の選別がしづらい。クリックで拡大し前後送りできる viewer(ライトボックス)を追加し、拡大確認しながら採用/除外・PNG保存まで完結できるようにする。

## スコープ

### やること

- viewer コンポーネント新規作成(src/ui/viewer.ts + src/style.css 追記): モーダルオーバーレイ。画像表示・前後送りボタン・「n / 総数」カウンタ・タイムスタンプ表示・閉じるボタン
- 開く導線: 結果一覧のサムネイルクリック(そのフレームから開く)+ 結果一覧ヘッダの「ビューアで見る」ボタン(先頭フレームから開く)。いずれもスキャン完了後(finalize 後)に有効化
- キーボード操作: ← → で前後送り、Esc で閉じる。背景(オーバーレイ)クリックでも閉じる
- 「採用のみ表示」トグル(viewer 内): ON にすると前後送りの対象が採用フレームのみになる
- viewer 内操作: 現在フレームの採用チェック切替(一覧と双方向同期)+ PNG 保存ボタン(既存 downloadOne を再利用)
- サムネ→フル解像度差し替え: 表示直後はサムネイル拡大で即表示し、裏で FrameSource.renderFull を実行して完成したら差し替える。生成済みはキャッシュ(上限付き、超過分は古い順に objectURL を revoke して解放)
- renderFull の直列化キュー: viewer のフル解像度生成と既存の PNG/ZIP ダウンロードが同じ renderFull(動画は共有 video 要素のシーク)を使うため、同時実行するとシークが混線する。main.ts に直列実行キューを設け、全ての renderFull 呼び出し(downloadOne / downloadZip / viewer)をそこ経由にする(既存の「PNG保存ボタン連打でシークが混線し得る」潜在問題も同時に解消)
- 前後送りの対象決定ロジック(「採用のみ」フィルタ考慮の次/前フレーム決定)は DOM に依存しない純関数に切り出して単体テストを書く
- README.md に viewer の使い方を追記

### やらないこと

- ズーム・パン(ピンチ拡大等)。画面にフィットする等倍表示のみ
- スライドショー自動再生
- スキャン進行中の viewer 起動(スキャン完了後のみ)
- 隣接フレームのフル解像度先読み(まずは表示中フレームのみ生成。体感が悪ければ後続改善)

## 方針

- viewer は resultsList と同様の「create 関数+ハンドル」パターン(createViewer(callbacks): ViewerHandle)で独立コンポーネント化する。フレーム配列・採用状態のオーナーは従来どおり main.ts であり、viewer は開閉時と変更通知時に渡されたデータを表示するだけにする
- 双方向同期: viewer 内の採用切替 → コールバックで main.ts の selected を更新し resultsList.applySelection を呼ぶ。逆に(viewer 表示中に)しきい値変更が起きたら main.ts から viewer へ通知して表示中のチェック状態・「採用のみ」フィルタの対象を更新する
- フル解像度差し替えは「表示中フレームと生成完了フレームが一致する場合のみ差し替える」トークン方式にする(高速送り中に、古いフレームの生成が遅れて完了して現在の表示を上書きする stale 表示を防ぐ)。キャッシュは frameIndex → objectURL の Map 管理で上限付き(名前付き定数、初期値 20)。上限超過時は古い順に revoke し、新ファイル読み込み時(handleFile)には全 revoke する
- ファイル切替(handleFile)時は viewer を強制クローズしキャッシュを全解放する。main.ts の既存セッションガード(session !== currentSession で静かに return)パターンを踏襲する
- アクセシビリティは最小限: role="dialog" + aria-modal="true"、開いたら閉じるボタンへフォーカス移動、閉じたら開く前のフォーカス位置(クリックしたサムネイル等)へ戻す
- 前後送り対象決定は純関数(例: findAdjacentFrame(frames, currentIndex, direction, adoptedSet, adoptedOnly) — 命名・配置は実装者裁量、src/core または src/ui 配下の DOM 非依存モジュール)として切り出し、Vitest で単体テストする(既存テストは DOM なしの node 環境で動いているため、DOM に依存させないこと)

代替案として viewer に状態(フレーム配列コピー)を持たせる案も考えたが、しきい値変更・ファイル切替との整合が複雑になるため、状態オーナーを main.ts に一本化する方式を採る。
