# 仕組み

## 完全クライアントサイド

動画/GIFの読み込み、フレーム抽出、変化点検出、ZIP生成まで、すべてブラウザのタブの中だけで処理されます。サーバーには何も送信されません。

## 軽量なスキャン

フレームを64×64のグレースケール画像に縮小して比較に使うことで、動画全体をスキャンする間もフル解像度の画像はメモリに保持しません。表示用にも小さなJPEGサムネイルしか保持しないため、数百フレームをスキャンしても軽快に動作します。

## 変化点検出アルゴリズム

各フレームを64×64グレースケールに縮小し、「直前に採用されたフレーム」との差分をタイル分割方式で計算します。

1. まず画素ごとの絶対差を求め、圧縮ノイズ等に由来する微小差(ノイズフロア未満)は0として切り捨てます。
2. 次に64×64のグリッドを8×8のタイル(局所領域)に分割し、タイルごとに(ノイズフロア適用後の)平均絶対差を0〜100%の差分率として計算します。
3. 全タイルのうち最大の差分率を、そのフレームの差分スコアとして採用判定に使います。

フレーム全体の単純平均ではなく局所領域ごとの最大値を見ることで、画面の一部だけの変化が全体平均に薄められて見逃されることを防ぎつつ、ノイズフロアによってノイズへの耐性も保ちます。

この差分スコアがしきい値以上であれば、そのフレームを新たに採用します。比較対象は直前の1サンプルではなく「直前に採用したフレーム」なので、ゆっくり進む変化の累積も検出できます。先頭フレームは常に採用されます。

## しきい値の即時再計算

スキャン中に保持しているのは各フレームの縮小グレースケールデータだけなので、しきい値を変更しても、保持済みのデータに対してこの判定をやり直すだけで済み、動画やGIFの再デコードは発生しません。

## フル解像度の再取得

ダウンロード時には、対象のフレームだけを元のソース(動画なら該当時刻への再シーク、GIFなら該当フレームまでの再合成)から改めて描画し、フル解像度のPNGを生成します。

## GIF生成

アニメーションGIFへの書き出しも、PNG/ZIPダウンロードと同じ「対象フレームだけをFrameSource.renderFullで都度取得する」仕組みに乗せています。採用フレームを1枚ずつフル解像度PNGとして取り直し、指定された最大幅への縮小・指定色数への量子化を行ってからGIFエンコーダへ逐次書き込み、書き込みが終わった元画像は破棄します。

透明画素(透過GIF由来の入力など)を含むフレームは自動判定し、透過を保持したままGIFへ書き出します(設定項目としては増えません。透明画素がないフレームは従来どおりの量子化で画質を変えません)。

GIFエンコーダはフレームを1枚書き込むたびに内部バッファをBlobチャンクへ吐き出してからバッファをクリアするため、JSヒープ上に抱えるのは現在のフレームと直近1フレーム分の圧縮結果程度にとどまります。GIF全体はBlobチャンクの配列としてブラウザが管理する領域に積み上がっていく形になり、エンコーダ内部にGIF全体分のバッファを溜め込むことはありません。

GIF入力から採用フレームを取り出す際のフル解像度合成(GifSource)も、直前までの合成結果を保持して続きから合成する逐次方式になっており、選択フレーム数に対してほぼ線形の時間で完了します(ビューアで前のフレームへ遡って表示し直した場合だけ、そこから改めて先頭から合成し直します)。
